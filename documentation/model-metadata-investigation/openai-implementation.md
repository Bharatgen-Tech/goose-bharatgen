# OpenAI implementation progress (2026-09-28)

Commits: `f548a74ca` (native endpoint routing/default), `eef47a3f9` (explicit reasoning overrides). These are incremental, not a complete removal of model-version rules.

- Direct `api.openai.com` connections configured through `goose/src/providers/openai_def.rs` now prefer Responses for model names other than `o1-mini*` when using the default `v1/chat/completions` path; compatible gateways, explicit custom paths, and versionless paths retain old routing. `OpenAiProviderBuilder` defaults to the conservative compatible-provider behavior. Official docs confirm GPT-4o and GPT-6 Astra support Responses, but o1-mini does not. The name-only `o1-mini` exception needs reconsideration for snapshots/aliases, and not every ID available from `/models` can necessarily serve text/tool Responses. Consider catalog tool-call/text metadata or explicit route configuration as the next guard. This preference changes wire behavior for direct OpenAI clients; test against live API before rollout.
- Default model changed from `gpt-4o` to `gpt-5.6-terra` as a balanced cost/quality option listed on OpenAI's model index. This is a product decision with access and price impact; the user may choose another model. No automatic price-based default selection exists.
- Chat and Responses payload formatters now honor explicit `ModelConfig.reasoning` before the legacy family matcher. Canonical reasoning metadata is copied into this field by `ModelConfig::with_canonical_limits`; unknown models still use name fallback. This does **not** replace the model-version effort matrix or remove `o1-mini` guards, because the available live metadata has no endpoint/effort/tool-compatibility guarantees for all aliases.
- The original `reasoning_mode` version gate was deferred initially, then removed in the follow-up below. Effort translation still uses catalog options with a conservative fallback. Clamping Off to Low is not equivalent to disabling reasoning; that behavior remains unchanged.

## Follow-up: reasoning_options and legacy model support

Correction: models.dev **does** supply `reasoning_options` with `type: effort` and `values` for many OpenAI models. We had not parsed it. The parser now stores `reasoning_efforts` on `CanonicalModel` (optional for older bundled data); the shared OpenAI effort mapper prefers it over the version table, with a conservative three-level fallback for entries without options. The bundled JSON has since been enriched with available OpenAI effort options, and live refreshes also parse them. The user approved dropping o1-mini: removed both shared Chat formatter rejection guards; native OpenAI routes it to Responses if manually configured, which is **not supported** by the OpenAI docs. Do not select it; a future change should reject unsupported non-tool models via authoritative capabilities rather than imply it is usable.

`openai-live-smoke.py` is an opt-in, billed test script (standard library only): run `OPENAI_API_KEY=... python3 documentation/model-metadata-investigation/openai-live-smoke.py` with the key already exported in your shell instead of embedding it in a command or file. It tests a short text response and a tool call, prints usage but not credentials; optionally set `OPENAI_SMOKE_MODEL`. It now also submits explicit `none`, `low`, and `medium` effort requests by default (override with `OPENAI_SMOKE_EFFORTS=high,xhigh,max` for additional, potentially costlier levels). It checks accepted requests and completion, not that reasoning occurred or that goose serialized the same request. It does not test streaming or replay. Do not commit any output containing your account metadata.

## Bundled metadata follow-up

The bundled canonical JSON now includes `reasoning_efforts` for 29 OpenAI entries copied from the corresponding `reasoning_options[type=effort].values` in models.dev on 2026-09-28. The shared mapper uses live or bundled catalog options first, falling back to `low`/`medium`/`high` for unknown aliases (rather than guessing version-specific `none`, `xhigh`, or `max`). This removes the hard-coded GPT-5/6 version matrix; an unknown alias may still have a different set of valid options. The mapping of goose Off to Low when `none` is absent is deliberately unchanged as requested. Snapshot-named models are subject to canonical alias resolution; verify if a snapshot diverges from its family.

No API call was made with a key here. The opt-in smoke test is ready for a human to run. Re-run focused/unit tests and clippy after any follow-up edits.

## Native routing follow-up

The native OpenAI provider now checks the active canonical catalog for a known text-input/text-output, tool-calling model before *implicitly* using Responses; it rejects known non-agent entries such as image/embedding models and `o1-mini` with a local error, rather than sending them to Responses. Unknown models fail closed on the implicit route with an instruction to refresh the catalog or set `OPENAI_BASE_PATH`. Explicit paths retain pass-through for unknown names; known non-agent models and o1-mini still fail because goose requires tools. The catalog does **not** encode endpoint support: known text/tool models could still fail on Responses, and old snapshot aliases inherit capabilities from their unversioned entry. Live testing remains necessary.

`OPENAI_BASE_PATH` provenance is carried from `goose/src/providers/openai_def.rs` into the provider: explicitly setting even `v1/chat/completions` opts out of automatic Responses routing, while `v1/responses` selects Responses. Existing versionless/custom gateway behavior remains unchanged. A persisted desktop default `OPENAI_BASE_PATH` may count as explicit; `OPENAI_BASE_URL` deliberately ignores that persisted value unless the path is set in the environment. This is a configuration migration consideration before release.

## Reasoning mode follow-up

The [OpenAI reasoning guide](https://developers.openai.com/api/docs/guides/reasoning#reasoning-mode) now documents `reasoning.mode` (`standard` or `pro`) for GPT-5.6 **and GPT-6** on Responses. Removed the GPT-5.6-only name matcher. `reasoning_mode` remains opt-in via request params; goose validates only the mode value and forwards it under `reasoning.mode` without a model-name support guess. The API will reject the option on unsupported models. No default mode is sent, so requests without this setting are unchanged. Pro mode can use more tokens and cost more; test it only with explicit consent. This does not modify Chat Completions or the separate effort mapping.
