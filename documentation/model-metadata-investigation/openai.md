# OpenAI provider and shared OpenAI formats

## Current path

`crates/goose-providers/src/openai.rs:378-400,508-513,776-789` selects Responses vs Chat Completions. A custom explicit Responses or Chat path wins; the default `v1/chat/completions` defers to `is_openai_responses_model`, while a versionless gateway Chat path remains Chat. `nearai`/`pleumrouter` are forced to Chat. The shared matcher (`crates/goose-provider-types/src/formats/openai.rs:1841-1855`) recognizes any `o` + digits or GPT-5/6 token, including hosted aliases. New families require changing code even if live catalog metadata exists. Routing to Responses based on `reasoning: true` would be incorrect for many non-OpenAI compatible models; avoid that substitution.

The same matcher drives `ModelConfig::is_openai_reasoning_model` and fallback `is_reasoning_model` (`model.rs:288-341`), strips legacy `-none/-low/-medium/-high/-xhigh` suffixes (`formats/openai.rs:1814-1839`), and influences system vs developer role, temperature and max token field in Chat (`formats/openai.rs:1722-1788`). Responses formatting (`formats/openai_responses.rs:667-760`) uses it to decide reasoning-effort emission and temperature. Thus changing routing alone does not eliminate version-dependent payload behavior.

`formats/openai.rs:1901-1939` chooses allowed effort from a hand-maintained matrix: GPT-5.4/5.5/5.6, GPT-6, GPT-6 Astra, `-pro`, and older GPT-5 families. `formats/openai_responses.rs:608-620,696-708` accepts `reasoning_mode` only for GPT-5.6, with an exact-version matcher. Both require manual changes as naming and supported efforts evolve; neither supported-effort sets nor endpoint route are represented by the catalog's generic reasoning boolean. `formats/openai.rs:1722-1727` also blocks `o1-mini` explicitly as lacking tools. xAI-specific effort support and mappings in `formats/openai.rs:1858-1900` are shared-format exceptions, not OpenAI provider defaults.

`openai.rs:446-505` has provider-name allowlists to remap token fields, system roles, `reasoning_effort`, and `tool_stream`. These are provider-compatibility constraints, not primarily model ID lists, but the `nearai`/`pleumrouter` conditional uses the model-name matcher to retain/remove `reasoning_effort`. `OPEN_AI_DEFAULT_MODEL` (`openai.rs:60`) is pinned to `gpt-4o`: a deliberate default to review independently of metadata. `known_models_from_registry` in provider metadata (`openai.rs:639`) already uses the canonical registry rather than a local version list.

## Existing metadata and limits

`openai.rs:537-584,737-765` discovers IDs from `/v1/models`, optionally probes `meta.n_ctx` for context, and merges configured `ModelInfo` with the canonical registry for discovered names (`goose-provider-types/src/base.rs:373-390`). Configured models win; `dynamic_models: false` uses only them; API endpoint-not-found can fall back to a configured list. None of this advertises whether a Responses endpoint is available. An explicit `base_path` can currently force the wire route; preserve that behavior. Suggested tests: new family missing the regex, aliases matching the regex but unsupported by a gateway, custom/versionless paths, catalog reasoning true but Chat-only, and effort/mode parameter differences across versions.
