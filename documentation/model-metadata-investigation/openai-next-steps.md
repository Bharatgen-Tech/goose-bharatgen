# OpenAI: proposed simplifications (2026-09-28)

Sources checked: [API docs](https://developers.openai.com/api/docs), [model index](https://developers.openai.com/api/docs/models), [Responses migration](https://developers.openai.com/api/docs/guides/migrate-to-responses), [reasoning guide](https://developers.openai.com/api/docs/guides/reasoning), and model pages for [GPT-6 Astra](https://developers.openai.com/api/docs/models/gpt-6-astra), [GPT-4o](https://developers.openai.com/api/docs/models/gpt-4o), and [o1-mini](https://developers.openai.com/api/docs/models/o1-mini). Pages can change; conclusions reflect the date above.

## Key correction to the initial audit

The `is_openai_responses_model` regex is **not** a Responses-compatibility test. The docs list Responses support for GPT-4o and GPT-5 Chat, while o1-mini does *not* support Responses. The matcher simultaneously controls route, reasoning handling, role, temperature and token field. Treat these as distinct capabilities. OpenAI recommends Responses for new projects while retaining Chat Completions support; a gradual move of the native OpenAI provider to Responses by default is plausible, but a blanket change to shared OpenAI-compatible clients is not.

## Proposal, in independently reviewable steps

1. Introduce a route policy for the **native OpenAI provider**, explicitly distinguishing it from `OpenAiProvider` used for compatible gateways. Respect explicit chat/responses base paths first; keep versionless and custom gateway paths conservative. For the official endpoint, prefer Responses for supported text/tool models, including GPT-4o, without using `reasoning` as a proxy. Do not send o1-mini to Responses. Investigate whether an explicit provider setting is preferable to a built-in exception for unsupported/legacy models. `/v1/models` only provides IDs, not reliable endpoint or effort support. Avoid silent retries from Responses to Chat after a failed streamed request (side effects and duplicate tool execution).
2. Separate `is_openai_responses_model` into routing, reasoning, and wire-parameter decisions. Use explicit `ModelConfig.reasoning`/canonical `reasoning` when available for reasoning-specific options, with a conservative name fallback for unknown aliases. Do not infer Responses eligibility solely from this boolean: GPT-4o is a counterexample. Regression-test explicit false, aliases, custom gateways, and legacy models.
3. Stop automatically translating unified thinking effort through the growing `openai_reasoning_efforts_for_model` version matrix (`formats/openai.rs:1901-1939`). Check how canonical metadata, user `request_params`, and OpenAI errors can support a model-agnostic default. OpenAI says effort values are model-dependent, including `minimal`, `none`, and `max`; models.dev `reasoning` is only a boolean. Preserve explicit user-supplied effort, but avoid a request-breaking default for unknown models. For Off, omission does **not** guarantee reasoning disabled; define a clear fallback/UI behavior instead of promising it. Retain narrow constraints only where verified, such as GPT-6 Astra not supporting `none` and GPT-5.6 `reasoning.mode` validation (`formats/openai_responses.rs:608-708`), until a capabilities source replaces them.
4. Revisit the `o1-mini` tool restriction (`formats/openai.rs:1722-1727`, `formats/databricks.rs:535-540`). Official model docs list no function calling or Responses support and recommend o3-mini instead. This is a valid compatibility guard, but it is overly broad (`starts_with`) and shared with third-party compatible endpoints. Scope it to official OpenAI where possible or keep a documented exact legacy exception; do not remove it merely because o1-mini is old.
5. Consider replacing the native default `gpt-4o` (`openai.rs:60`) with an intentional supported agent model: OpenAI's current model index recommends GPT-6 Astra for complex reasoning/coding, GPT-5.6 Terra for cost balance, and GPT-5.6 Luna for latency/cost. Changing the default affects price, access, and UX and should be a separate product decision. Keep older models user-selectable; avoid shipping an ever-growing hand-maintained default list.

## Verification questions before implementation

- Distinguish native host, Azure/Databricks, and custom `openai` base URL. Existing custom-path and `nearai`/`pleumrouter` exceptions (`openai.rs:382-400,508-513`) must retain their semantics unless intentionally migrated.
- Test GPT-4o on Responses, o1-mini rejection on Responses, unknown future reasoning family, explicit Chat route with a reasoning model, and aliases whose canonical entry differs from their wire name.
- Test reasoning parameters independently: explicit `none` versus Off, omission, version-specific values, `reasoning_mode`, temperature, developer/system roles, and `max_tokens` versus `max_completion_tokens`. Avoid changing Chat-format provider compatibility when changing native routing.
- Native Responses path must preserve conversation replay, tool calls, streaming, usage, and context/vision constraints; examine the existing `stream_for_model` integration tests before switching defaults.
