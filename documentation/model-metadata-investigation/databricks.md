# Databricks serving endpoints and AI Gateway V2

## Serving endpoints (`crates/goose-providers/src/databricks.rs`)

Defaults and a small static known-model list live at `:72-82`; actual discovery uses `api/2.0/serving-endpoints` (`:787-844`). Endpoint metadata may include upstream model/provider and `openai/v1/responses` among served-entity `api_types` (`:240-335`). Routing `:218-225,597-622` **prefers endpoint API-type metadata** and falls back to the shared OpenAI model-name matcher only when metadata is unavailable; metadata failures are cached for discovery but retried for routing (`:54-68,~470-490`). This is an important existing precedent to preserve. The first-hop API type is kept when following model-serving indirections (`:385-454`). Tests at `:1083-1127` cover metadata priority and fallback.

Remaining name inference: `:189-194,290-296,497-512` classifies Claude/reasoning by substring or OpenAI regex, even when upstream provider is returned, and uses the upstream model to look up context and vision in the canonical registry. Inference `:602-681` uses upstream model for vision, Responses request formatting/effort, and Anthropic-style chat formatting. Shared `formats/databricks.rs:505-625` branches on `claude`, OpenAI regex, and `o1-mini` to decide thinking, temperature, max-token fields and cache breakpoints; `cache_semantics.rs:23-36` independently checks for `claude`. Aliases can route correctly from API types but still receive a mismatched payload when the upstream ID is unavailable.

## AI Gateway V2 (`crates/goose-providers/src/databricks_v2.rs`)

Defaults and known models are pinned at `:82-84`, while `:274-340,530-570` obtains names dynamically from paginated Gateway endpoint and model-service catalogs. Endpoint names are excluded from discovery by an embedding/BGE/GTE name heuristic; model services use `supported_api_types` when present and inspect the **leaf** name only if absent. This filtering is itself release-sensitive and can hide chat-capable endpoints with misleading names; absent metadata, the API route cannot be inferred from discovery alone.

Routing (`:219-255,514-526`) extracts the FQN leaf for model services, then uses OpenAI `o`/GPT-5/6 matcher or `gpt-5`/`gpt5` substring for Responses, `claude` substring for Anthropic Messages, else MLflow Chat. The GPT-5 rule is broader than the shared matcher, but also excludes future unrelated OpenAI naming families. A custom model-service alias whose leaf says neither GPT nor Claude can select MLflow despite the service supporting another route. Catalog `supported_api_types` is currently used only for discovery, **not** to select a route at inference. Confirm what endpoint and model-service APIs expose per-name before changing this: API type metadata might be the best replacement, but discovery of a name alone is insufficient. Tests at `:671-699,800-808,903-970` encode existing alias/FQN expectations.

`databricks_v2.rs:258-270,376-400` additionally recognizes GLM 5.3 and Kimi K3 to clamp always-on reasoning effort, using shared `ModelConfig` name parsing. For FQNs it substitutes `model-service` into the Chat formatter to avoid namespace text triggering format heuristics, then restores the real model ID. That guard documents a real hazard with full-name substring checks. Keep route selection and payload capabilities separate when refactoring. Suggested tests: API types contradicting an alias name, unknown GPT family, misleading namespace vs leaf, unknown embedding family, absent metadata fallback, and transient metadata errors without poisoning routing.
